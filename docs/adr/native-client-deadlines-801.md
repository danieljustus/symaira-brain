## Decisions

1. Use the already pinned Tokio1.53.1 native `NamedPipeClient` directly for the Windows client. Interprocess2.4.4's busy-connect constructor can spawn blocking work; its Tokio flusher calls `FlushFileBuffers` through `spawn_blocking`, and unflushed stream drop can hand a handle to a linger pool. Tokio documents that runtime drop waits indefinitely for blocking work. A timeout around the future does not cancel that blocking owner. Those are actual source findings; they do not attribute the old native stall's unknown phase.
2. Native open keeps the original common `to_string_lossy` endpoint spelling used by client, server creation and wake, byte mode, read/write access and Tokio's identification security-QoS default. The initial direct-OsStr client-only checkpoint591 and its integrated successorc919 are preserved before correction: an unpaired UTF16 code unit would select a different endpoint from the unchanged server. Root chose a bounded deadline change with the existing relation; a full raw-WTF16 cutover must update all three owners together. This is source evidence, not an actual Windows/Go result. Only native `ERROR_PIPE_BUSY` retries, using an async25ms sleep under the existing connect timeout. Missing/refused endpoints retain their unavailable mapping. The original payload check, write/flush/read body, response/frame limits, JSON decode and error mapping stay byte-identical. Unix transport, server ACL/remote refusal, peer policy, startup/child deadlines and provider/key owners are unchanged. No dependency or unsafe API is added.
3. Do not use shutdown-background/timeout to abandon blocking work or handles. The client introduces no blocking connect/flush task or interprocess linger owner. Tokio's flush itself returns ready without `FlushFileBuffers`. The existing response protocol confirms server processing. This is source preparation: native Windows cancellation, pending I/O and actual process completion still require real proof. Pinned Mio's drop source cancels pending reads/connects and treats outstanding writes separately; source reading alone is not a claim that every pending write handle has completed native cleanup.
4. An ignored Windows test is mandatory in both Windows CI jobs through an explicit invocation. Its isolated owned child has an external8s watchdog and file-backed raw stdout/stderr/status. It exercises an unread request, a request exceeding advertised input capacity, a busy single-instance pipe and all eight concurrent real clients. The unread peer stays held until the client returns; the ordinary client timeout is150ms in that fixture. The watchdog rejects a stall or child failure and retains phase logs. Existing complete eight-way CLI autostart assertions and platform contracts remain intact. Three additive real Windows endpoint-pair scenarios keep ASCII and valid Unicode controls and an unpaired-surrogate/literal-replacement pair. They assert two exact owner/request dispatches plus successful stop/wake join; restoring the preserved OsStr-only client is a meaningful prepared negative control. All seven scenarios are prepared, not executed observations.
5. CLI diagnostics own files rather than waiting for EOF from inherited pipes. The CLI wait remains15s. Kill/reap cleanup has a separate bounded2s wait. Begin, launch and spawned/PID events precede waiting; complete raw snapshots, status, timeout/error and file hashes reach their sidecar before assertions or rethrow. A timeout or failed launch cannot become an accepted child outcome. Files are adjacent to the owned report outside the product's filesystem snapshot. They represent the owned CLI wait/cleanup snapshot and make no descendant wire/exit claim. This avoids Python's Windows `subprocess.run` timeout path performing another unbounded `communicate` after kill. The original journals do not prove that this path caused their silence.
6. The full process and registry reports are started before operations can fail. Partial case records and failure type/message survive an exception. Reporting does not change the parity comparators, their original negative controls or product expectations.
